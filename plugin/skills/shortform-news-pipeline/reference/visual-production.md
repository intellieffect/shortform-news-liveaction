# 발화를 화면으로 만드는 제작 계약

새 start는 `visual-system.visual_contract`와 보존 요청에 `visual-explanation@1`을 연결한다. 기존 확정편에는 소급하지 않는다. 파일·필드·도구 사용은 품질 증명이 아니다. [데이터 계약](../../../../docs/specs/editorial-concept.schema.md)과 이 문서를 함께 적용한다.

## 먼저 보일 일을 정한다

전체 기사·자료와 원고를 왕복하며 각 개념의 `visual.purpose`를 explain/observe/quote/atmosphere 중 선택하고 `focus`에 먼저 보일 대상을 적는다. 핵심 설명은 `moments`에 발화 줄, 같은 대상, 작용 또는 비교 관계, 눈에 보이는 결과를 연결한다.

`subject`·`action`·`result`는 **화면에서 관찰될 것**을 적는 자리다. 발화를 다른 말로 옮긴 문장을 여기에 쓰지 않는다. 나레이션이 화면에 맡긴 대상·관계·변화가 실제로 식별되는지 판단한다. 소리를 끄고 보는 것은 그 역할을 확인하는 보조 점검이며, 사진만으로 모든 사실·용어를 설명하라는 요구가 아니다. `subject`는 화면에서 짚을 수 있는 하나의 대상이고(형용사나 범주어가 아니다), `action`은 그 대상에 일어나는 작용이거나 두 대상 사이에 성립하는 비교 관계이며(질문이나 주제어가 아니다), `result`는 작용이 끝난 뒤 눈에 남는 차이다. 명사 라벨이나 화살표가 있다는 사실만으로 동사가 수행됐다고 판단하지 않는다. 수치 비교는 공통 기준과 차이가 결과이며 반드시 동작일 필요는 없다. 관측·인용·호흡 구간에 과정 도해를 강제하지 않는다.

핵심 설명을 설계할 때 **이 화면이 어떻게 잘못 읽힐 수 있는지**와 **성공했다면 화면에서 무엇이 보일지**를 한 줄씩 정한다. 앞의 것은 같은 그림을 반대 방향·다른 대상·다른 인과로 읽을 실제 가능성이고, 뒤의 것은 그때 관찰될 구체적인 변화다. 둘은 기존 제작 노트(direction.md/decisions.md)나 해당 moment의 기존 텍스트에 남기며 **새 필수 JSON 필드를 만들지 않는다.** 모든 개념에 두 줄을 채우는 서식이 아니라 오독 가능성이 실제로 보이는 핵심 설명에서 쓰는 판단 도구다. 오독 쪽이 더 그럴듯하면 라벨을 붙이기 전에 대상·구도·작용·재료를 바꾼다.

`visual.realization`은 method(source/generated/code/hybrid), asset_ids, job_ids로 재료와 생성 계획에 연결한다. **역할은 구현을 시작하기 전에 정한다.** 이 설명에 필요한 외형(형태·질감·빛·공간감)과 필요한 움직임(무엇이 어떻게 변해야 하는지)을 먼저 따로 적고, 그 둘을 각각 무엇이 감당할지에서 method와 `generated_role`·`code_role`이 나온다. 외형만 보고 역할을 정하면 움직임이 남은 수단에 떠넘겨지고, 그때부터는 설명이 아니라 구현 편의가 화면을 정한다. 코드가 설명에 적합하면 사용한다. 제작 편의만으로 단순 도형을 먼저 만든 뒤 남는 외형만 생성하지 않는다. 필요한 미술과 작용에서 출발해 수단을 정한다.

## 생성과 합성

Higgsfield는 배경·외형뿐 아니라 빛의 진행·산란, 유체·가스의 변형, 응집·붕괴 등 **동작 전체**를 만들 수 있는 선택지다. 설명의 움직임을 생성에 맡기는 것은 정식 선택지이며, 같은 움직임을 코드로 합성하는 것도 그렇다. 둘 중 하나를 채워야 할 비율이나 금지된 수단은 없고, 이 설명에 필요한 미술과 작용이 선택 근거다. 실제 가능한 도구·모델을 확인한다. 연결된 MCP를 사용하라는 사용자 지시가 있으면 해당 경로를 우선한다. 코드로 수치·축·문구·배치·발화 타이밍을 제어하면서 생성 동작을 합성할 수 있다. 도구 호출 또는 정지 이미지 생성만으로 모션그래픽 제작을 완료했다고 하지 않는다.

`visual-system.generation_jobs`에 생성 예정/진행/실패/기각/채택 작업을 기록한다. id, kind(image/video/overlay-video), purpose, status는 계획부터 적는다. 호출 후 실제 provider/model, 편 상대 prompt_path, 가능한 job_id, output 원본, observation을 연결한다. 채택 자산에는 media.assets[].generation_job을 넣는다. 원본과 합성용 파생본은 구별한다. 생성 역할은 realization.generated_role, 코드 역할은 code_role에 짧게 적는다. 역할이 없으면 억지로 만들지 않는다.

생성 요청문에는 **눈에 보일 작용과 결과**를 담는다. 대상의 외형·질감·조명만 적은 요청은 정지한 그림을 돌려주기 쉽다. 무엇이 어디에서 어디로 가는지, 무엇이 얼마나 변하는지, 끝났을 때 화면에 무엇이 남는지를 문장에 넣는다. 동시에 그 문장이 **다르게 읽힐 여지**를 줄인다 — 방향(안·밖, 위·아래), 순서(먼저·나중), 인과(무엇이 무엇을 일으키는지), 시점과 척도가 모호하면 모델은 그럴듯한 다른 현상을 만들어 온다. 애매한 은유어 대신 물리적으로 관찰 가능한 서술을 쓴다.

실패하면 같은 목적에 맞게 입력 이미지·동작·구도·분리 생성·다른 자료 또는 코드를 재선택한다. 생성 영상이 반대 작용을 보이는데 라벨로 맞는 뜻을 씌우지 않는다. 계정·도구 실패는 그대로 기록하고 resume에 미해결 상태를 남긴다. 생성 횟수나 사용 비율은 통과 기준이 아니다.

## 선택적 표현 시험 — first-core-scene@5

새 편은 원고·자료·표현 방향이 정해지면 음성과 전체 시안 제작을 진행한다. 모든 편에 첫 장면 시안이나 독립 검수를 요구하지 않는다. 원고·주요 자료·표현 수단의 선택을 바꿀 구체적인 불확실성이 있을 때만 해당 부분을 먼저 시험한다. 단순한 밝기·질감·배치 개선 가능성은 시험을 여는 이유가 아니다. 시험 결과가 제작 선택을 바꾸지 않으면 시험을 생략한다.

시험 전 기존 direction.md/decisions.md에 **불확실한 질문 / 진행할 수 있다고 판단할 관찰 / 실패 시 대안**을 짧게 적는다. 별도 필수 기획 서식을 만들지 않는다. 예: “분출물이 기존 주름을 실제로 가리는가 / 주름이 먼저 보이고 분출물 뒤에서 사라짐 / 생성 대신 실사와 코드 합성으로 전환”. 외형·합성 가능성은 제작자가 보고, 독립적인 의미·오독 관찰이 필요할 때만 사전 승인된 scene-judge를 호출한다.

정지 상태로 답할 질문은 이미지로, 동작이 필요한 질문은 짧은 동영상으로 시험한다. 실제 배경·자료와 공통 자막을 포함하는 합성 시험에는 [scene-proof 도구](../../../../docs/SCENE-PROOF.md)를 재사용한다. 시청자가 실제로 받게 될 앞뒤 장면·자막·발화 맥락을 함께 제공한다. 초견에서는 제작자가 원하는 정답과 구현 처방을 숨기되 시청 맥락을 제거하지 않는다. 실제 음성 없이 발화 타이밍을 최종 판단하거나 정지 이미지로 동작을 통과시키지 않는다. 무음 확인은 화면 역할의 보조 점검이며 모든 설명을 한 장면이 독립적으로 완결해야 한다는 뜻이 아니다.

검수는 **시험 질문**에 답한다. 설계에 적힌 형태·궤적·실루엣·표현 수단은 작업 가설이다. 사실을 보존하면서 의도한 이해가 전달되면 제작자가 가설을 갱신할 수 있다. 모든 moments, 레퍼런스의 미술 완성도, 픽셀 좌표를 초기 통과 조건으로 만들지 않는다. 의도 대조는 필요한 시험에서만 이어가며 모든 시험에 두 단계 호출을 요구하지 않는다.

질문에 답을 얻으면 **채택 / 표현 변경 / 판단 보류** 중 제작 선택과 이유를 기존 노트에 남기고 시험을 끝낸다. 관찰 원문은 보존하고 부수적인 개선점은 전체 시안으로 이월한다. 같은 지적이 남았다는 이유만으로 새 버전을 만들지 않는다. 재시험은 다른 결과를 기대할 구체적인 변경이 있을 때만 하며, 같은 불확실성이 반복되면 미세 조정 대신 자료·구도·표현 수단을 다시 선택한다. 이 원칙은 draft·정식 제출·생성 재요청 모두에 적용한다. 변경 없는 실물을 기록용으로 재렌더하지 않는다.

시험은 음성 착수 게이트가 아니며 시험의 존재·실패·미확인이 음성을 자동 차단하지 않는다. 실제 사실 왜곡이나 표현 실패를 발견하면 해당 표현을 수정·교체하며 pass로 바꾸지 않는다. 관찰 verdict와 제작 선택은 구별하고, 미확인이나 이월 사항은 전체 시안에서 회수한다. 시험 결과를 최종 시각·음향·사실 검수로 수입하지 않는다.

`@1`~`@4`로 시작한 편은 보존된 초기 착수 계약을 따른다. [구형 시안·조건부 착수](../../../../docs/SCENE-PROOF.md#기존-편의-초기-독립-검수--first-core-scene14)를 유지하며 새 규칙을 소급 적용하거나 저장된 요청·검수 원문을 바꾸지 않는다.

## 화면 글자

고정 나레이션 자막은 기존 공통 런타임을 유지한다. 추가 문구는 concepts.elements에서 kind:text인 요소의 text에 정확히 적는다. 이름·수치·단위·귀속·의미를 바꾸는 조건을 우선하고, 같은 설명을 자막 위에서 다시 읽게 하지 않는다. 인용·표의 본문은 내용에 필요한 만큼 설계한다. 일률적 글자 수·라벨 수로 품질을 판정하지 않는다.

`screen-text@1` 편(start가 request.json에 기록)은 다음 두 가지를 화면에 넣지 않는다. editorial:check가 오류로 막는다.

- **표기 텍스트**: 상상도·AI 재구성·개념도·원리 도해·관측 아님·측정 아님·모델 예측 같은 재료 성격 표기와 사진·자료 출처·라이선스·크레딧. 출처와 생성 고지는 `02_production/CREDITS.md`에 적고 게시 설명란으로 전달한다. 예측·가정·조건은 나레이션 문장("모델대로라면", "계획으로는")이나 화면의 형태 차이(실사와 도해의 재료 구분, 빈 기호와 채운 기호)로 전달한다. `role: provenance` 텍스트는 이 편에서 허용하지 않는다.
- **설명 텍스트 중복**: 나레이션을 다시 적는 문장·체크리스트·여러 줄 설명. 나레이션이 화면에 직관적으로 표현되면 충분하다. 남는 문구는 받아 적기 어려운 고유명·수치·기호처럼 대상에 붙는 짧은 키워드다.

사용자 원문(2026-09-23): "상상도, 출처와 같은 텍스트 제거", "장면에 불필요한 설명적인 텍스트 삭제. 나레이션이 화면에 직관적으로 표현되기만 하면 됨." 검사는 문구 자체만 본다(`scripts/lib/screen-text-policy.mjs`). 짧은 키워드가 기준에 붙어 읽히는지는 실물 검수가 본다.

### 키워드는 기준에 붙인다

화면 글자는 하나의 대상이나 기준에 붙는 키워드다. 의미는 글자가 아니라 형태의 차이와 움직임으로 전달한다.

- **이름**은 지시선·위치 표시로 해당 대상에 붙인다.
- **성분·상태**는 해당 층·영역에 붙인다(괄호·경계·같은 색).
- **수치·연도·비율**은 같은 척도의 눈금·기준 도형·비교 대상·이전 상태와 함께 둔다. 기준을 화면에 세울 수 없는 숫자·연도는 올리지 않고 나레이션에 맡긴다. 실사 위에 선 하나와 숫자만 얹은 오버레이는 기준이 아니다.

배치 전에 문구마다 두 가지를 확인한다. ① 이 글자를 지우면 화면에서 무엇을 잃는가 — 잃는 것이 없으면 지운다. ② 이 숫자·이름은 화면의 무엇과 비교되거나 연결되어 읽히는가 — 답이 없으면 기준을 그리거나 지운다. 사례는 [공통 레퍼런스](visual-references.md)의 scale(공통 영점), area(기준 영역 1에서 확장), observation(위치창)이다.

사용자 원문(2026-09-23): "오버레이 텍스트는 실사 위에 선 하나·숫자만 얹은 오버레이라 기준과 관계가 안 읽히는 문제가 있어." 이 판단은 문구만으로 기계 검사할 수 없으므로 제작자의 배치 판단과 shot-judge·editorial-judge 관찰로 확인한다.

신규 장면의 추가 텍스트는 `src/editorial/ScreenText.tsx`의 EditorialScreenText를 사용한다. elementId와 eventId를 연결하며 좌표·색·서체·크기는 style로 자유롭게 지정한다. 컴포넌트는 concepts의 정확한 문구를 읽고 timeline 등장/퇴장을 적용한다. globalFrame은 필수이며 Sequence 바깥에서 얻은 전역 프레임을 전달한다. 지역 프레임을 자동 추정하지 않는다. 장식·라벨 스타일 템플릿이 아니다.

resume과 intent의 screen_text는 선언 문구·동시 자막·시점 누락을 보여주며 render_text_audit는 JSX 직접 문구를 진단한다. 동적 문자열·이미지 속 글자까지 자동 검출했다고 해석하지 않는다. 실제 합성 화면에서 자막과 함께 확인하고, 읽기 부담이 크면 대상·구도·동작·재료 변경부터 검토한다.

## 재개와 검수

`context.work.visual`의 tasks에서 설명 설계·생성·문구 연결 문제를 확인한다. `@5`는 필수 scene-proof 작업을 만들지 않고, 실행한 시험의 시안·관찰·원문 연결과 최신성은 `scene_proofs`에 남긴다. 시험 질문·선택 이유·이월 사항은 기존 제작 노트에서 읽는다. 기술 상태나 시험의 usable은 최종 품질 판정이 아니다.

전체 시안에서 실제 발화·앞뒤 흐름과 함께 이월 사항을 확인하고 [전체 검수·수정](review-loop.md)을 수행한다. 최종 visual 검수의 explanations에는 concept_id/moment_id, 실제 observed_subject/action/result, text_dependency, evidence, basis(observed/code_inference/unverified), verdict(pass/changes_requested/unverified)를 기록한다. 핵심 설명 실패는 blocking, 확인 수단 부재는 incomplete로 구분한다. 코드 계산·정지 표본·초기 시험만으로 최종 동작 설명을 통과시키지 않는다. 최종 동작 설명의 pass에는 해당 개념의 실제 연속 확인 범위가 필요하며, 전체 이야기·호흡·음향은 별도로 검수한다.

최종 text_review는 실제 추가 문구와 고정 자막의 읽기 부담을 observation·evidence에 연결한다. JSX·중복 경고는 개수로 판정하지 않는다. 수정 뒤에는 원래 문제가 어떻게 달라졌는지 실제로 재확인하며 바뀌지 않은 부분까지 무조건 다시 검수하지 않는다.
