# 개정 — 규칙을 늘리고 옮기고 집행하는 법

> **이 파일은 제작 루프가 아니라 개정 루프에서 읽는다.** 규칙을 새로 쓰거나, 옮기거나, 가드를 붙이거나, 스킬 파일을 쪼갤 때.
> 근거는 [규칙 감사 1차](../../../../docs/research/2026-09-01-skill-rule-audit/summary.md) · [소급 실측 1차](../../../../docs/research/2026-09-01-skill-rule-audit/retro.md) · [규칙 위반의 기전](../../../../docs/research/2026-09-01-solar-swirl-v1-review/summary.md).

## 적용 범위

연출 피드백은 먼저 편별 문제·선택·수정 결과로 보존한다. 기사 위임 제작의 이야기·자료 구성·몰입 문제를 곧바로 필드·전역 금지·가드로 바꾸지 않는다. 아래 승격 절차는 반복 가능한 기술 계약을 집행할 때 적용한다. 선택의 적합성은 실물 검토와 새 편 제작으로 검증하며, 기록 필드가 채워졌다는 사실로 품질을 증명하지 않는다.

## 1. 기술 규칙 하나를 만드는 5단계

**발견 → 규칙 → 데이터 필드 → 가드 → 소급 실측.** 앞 단계를 건너뛰면 뒤가 헛돈다.

| | | 5편 「3단 판정」 예 |
|---|---|---|
| ① 발견 | 무엇이 잘못됐나. **사용자 원문을 그대로 인용**해 둔다 | *"소용돌이나 고무줄 같은 건 실제 영상으로"* |
| ② 규칙 | 한 문장. 근거·경위는 여기 쓰지 않고 `docs/research/` 에 링크 | 자·컴퍼스로 그릴 수 있나 → 코드 도해, 아니면 실사 |
| ③ **데이터 필드** | 그 규칙이 적용되는 **데이터에 자리를 만든다** | `layer43_plan[b].tier` · registry `draw_tier` |
| ④ 가드 | 그 필드를 읽어 판정한다. **경고에는 `[코드]`** | `check-shots` `[draw-tier]` · `gate 4-3` E5 |
| ⑤ 소급 실측 | 옛 편 전부에 돌린다 → §3 | 1~4편 42건 → 죽는 것 0건 |

**③ 이 핵심이다.** 규칙이 문장으로만 있으면 그 데이터를 만질 때 문맥에 없다 — 5편이 라벨을 어긴 기전이 정확히 이것이다(`label_tag@1` 의 `rules` 에 "카드 대용 금지"는 있었고 "연속 반복 금지"는 없었다).

> **규칙은 그 규칙이 적용되는 데이터 옆에 둔다.** registry `primitives[].rules[]` · `templates/*.json` 의 `rules[]`·`_comment` · `docs/specs/*.schema.md`.

## 2. 오류인가 경고인가

| 판정 | 기준 |
|---|---|
| **오류** | 정당한 예외가 **없다**. 데이터만 보면 참·거짓이 갈린다 |
| **경고 + `[코드]`** | 정당한 예외가 **있다**. 편별로 통과가 실측되면 `pilot.json.guards[]` 선언으로 **오류로 승격** |
| **경고(코드 없음)** | 예외가 흔하다 — `static>4s(B3)` · `같은 씬 label 두 번` · `upscale` |
| **「판단한 흔적」 검사(D형)** | 판단 자체는 못 본다. 근거를 **값으로** 남기게 하고 그 값을 본다 |

**D형은 문자열이 아니라 값으로 받는다.** `plan.why` 에 `"3단 판정"` 이 있는지 보는 검사는 **넉 자 적으면 통과**했다. 열거값(`tier: 1|2|3a|3b|3c`)이면 그 우회가 막힌다.

**착수 게이트와 사후 가드를 나눈다.** 사후 가드는 만든 **뒤에** 잡으므로 되돌아감을 못 막는다 — 5편이 되돌아간 5건 중 사후 가드가 막을 수 있었던 건 2건뿐이었다. 순서를 강제해야 하는 규칙은 `npm run gate -- <id> <층>` 으로.
착수 게이트는 **구현 전** 상태를 검사한다 — registry 필수 필드 중 `impl` 만 예외인 이유가 이것이다.

## 3. 규칙 승격 게이트 — 한 편의 판단이 전편 규칙이 되기 전에

`rules.md` 규칙 중 편을 인용한 48개의 **40개가 단 한 편만 인용**하고, 분포는 **최신 편 가중**이다(5편 14 · 4편 10 · 2편 8 · 3편 7 · 1편 1). 기본값이 「전편 규칙」이면 최신 편의 취향이 매번 규칙이 된다.

| 단 | 이름 | 사는 곳 | 승격 조건 |
|---|---|---|---|
| 1 | `pilot_rule` | 그 편 데이터 안(**`layer43_plan.layout.pilot_rules`** — `rules` 는 표준이라 손대지 않는다) | — **기본값. 여기 머물러도 된다** |
| 2 | candidate | `rules.md` | 가드를 같이 썼다 |
| 3 | rule | `rules.md` 정식 | **소급 실측**: 옛 편 전부 위반 0, 또는 위반 편을 설명 |

**소급 실측** = 새 규칙의 가드를 **옛 편 전부에 거꾸로 돌린다**(`npm run check:all`). 위반이 나오면 네 부류로 가른다:

| 부류 | 뜻 | 예 |
|---|---|---|
| 위반 0 | 잘 되던 편들이 이미 지키던 선 → **승격** | 팝 연도 제외 |
| **후보 0** | 해당 사례 자체가 없다 → 「무해」이지 「이미 지키던」이 아니다. **구분해서 적는다** | `continuous_with` |
| 제정 이전 상태 | 규칙이 그 편에서 만들어졌고 그 편의 옛 상태가 남았다 → 규칙 성립 | 생성 count 1 (2편 b08) |
| **기록된 예외** | 사유가 이미 데이터에 있다 → **규칙 문장이 불완전했다.** 예외 조항을 규칙에 넣는다 | 검정 배경 0 (3편 b09) |
| **최신 편이 어겼다** | 규칙은 옳고 **가드가 없었다** | AI 고지 위치 (5편 5비트) |

기계 소급이 안 되는 규칙(D·E 유형)은 **「소급 불가」로 표시**하고 일반화를 주장하지 않게 둔다. 표시 없는 것이 제일 나쁘다.

**편별 준수는 `pilot.json.guards[]` 에 등기한다** — 실측으로 통과하는 것만 선언한다. 선언은 「이 편이 이 규약을 지킨다」는 등기이고, 미선언은 「못 지킨다」는 기록이다.

## 4. 옛 편은 되돌리지 않는다

납품본이라 회귀 위험이 값어치보다 크다. 새 편·새 부품부터 계약을 쓴다(rules §5c).
그래서 가드는 **편별 세대**로 굴린다 — 옛 편은 `guards` 를 비우고 경고로 남긴다. 데이터를 고치는 게 아니라 등기를 안 하는 것이다.
편의 재현 가능성은 `pilot.json.engine_commit` 이 기록한다 — 납품편의 산출물은 mp4+md5 이지 재렌더 보장이 아니다.

**가드를 추가하면 `npm run check:all` 로 옛 편 ERROR 0 을 실측한다.** 코드만 쓰고 통과했다고 하지 않는다 — **고의 결함을 주입해 발화를 확인**한다(가장 좋은 것은 과거 커밋의 진짜 결함이다: `gate.mjs` 는 5편 4-3 착수 커밋 `20359fb` 에 돌려 17건을 실측했다).

## 5. 실패 모드 다섯 — 전부 실물로 관측됐다

| | 실패 | 관측 |
|---|---|---|
| F1 | **만든 줄 알았는데 안 도는 가드** | 계획↔실물이 5편에서만 작동 · `check-mc-spec` 는 파일 없으면 통과 · registry `impl: implemented` 거짓 2건 · `check-all` 코드 파서가 숫자를 못 읽어 `gen-count-1` 승격 무효 |
| F2 | **규칙이 작업 문맥에 없다** | 라벨을 복사하는 순간 `rules.md` 63개 중 하나가 떠오르지 않는다 |
| F3 | **확인 방법이 규칙의 일부가 아니었다** | 안전영역을 지켰다고 믿었는데 bbox 를 한 시점만 쟀다 |
| F4 | **사본이 갈라진다** | 크로스디졸브가 `layers.md §B` 표에서만 10f, 나머지 네 곳은 8f · **편별 복제본은 반대로 오염된다** — 5편 `layout.rules` 15줄 중 4줄이 4편 것(2026-09-02 실측) |
| F5 | **최신 편 편향** | 최신 편이 규칙을 가장 많이 만들면서 옛 규칙을 조용히 깬다 |

F1 이 제일 위험하다 — **가드가 있다고 믿고 다음 편을 시작하면 그 자리에서 또 3판을 간다.** 대책: 가드 코드명에 **숫자를 쓰지 않고**(파서 함정), 문구가 아니라 **코드로** 매칭하고, 추가할 때마다 **고의 결함으로 발화를 실측**한다.

## 6. 파일 배치 — 기준은 주제가 아니라 **로드 시점**

이 스킬은 progressive disclosure 구조다(`SKILL.md` 65줄만 항상 로드).

| 로드 시점 | 파일 | 줄 |
|---|---|---|
| 항상 | `SKILL.md` — 라우터. 한 줄 원칙과 「어디를 읽나」만 | 72 |
| 편 착수·단계 전환 | `stages.md` · `sessions.md` | 88 · 102 |
| 그 단계에서 앞 편들이 굳힌 것 | `stages-log.md` | 119 |
| 3′ 트랙에 들어갈 때 | `track-3prime.md` | 146 |
| 비트를 만지는 동안 | `rules.md` · `layers.md` · `schemas.md` | 201 · 112 · 65 |
| **마감(4-6)에만** | `rules-finish.md` | 44 |
| 명령을 칠 때 | `commands.md` | 194 |
| 커버 구상·제작 | `cover.md`(판단) · `cover-build.md`(생성·검수) · `cover-examples.md`(이미지 예시) | — |
| **규칙을 고칠 때** | **이 파일** | 121 |

### 몰림 방지

1. 파일 안에서도 **로드 시점으로 소제목**을 나눈다 — 불릿 10개 초과는 목차가 필요하다는 신호.
2. **≈200줄 또는 로드 시점이 둘이 되면 쪼갠다.** **2026-09-02 완료 — 최대 `rules 201`**(불릿 쪼개기로 2줄 늘었다. 다음에 넘치면 §5c 도해 46줄이 첫 분리 후보다). 무엇을 어떻게 갈랐나:
   - `stages 337` → `stages 88` + `track-3prime 146`(별도 트랙) + `stages-log 119`(굳어진 것·편별 원문)
   - `rules 233` → `rules 199`(비트마다) + `rules-finish 44`(마감에만). 옛 §11b 는 [§3](#3-규칙-승격-게이트--한-편의-판단이-전편-규칙이-되기-전에) 로 흡수
   - 당시 커버 문서를 구상·실행 두 파일로 나눴다. 내용은 2026-09-06 생성 방식으로 교체했다. 현재 로드 경로는 위 표를 따른다.
   - `commands 206 → 192` — **편 이름 절 3개(2·3·4편 추가 명령)를 주제 절로 접었다.** 편별 유래는 줄 끝 `(N편)`. 중복이던 「검토 사다리」는 commands 를 단일 소스로.
3. **이관은 잘라내기가 아니라 「한 줄 + 링크」** — 원 자리에서 맥락이 사라지면 안 된다.
4. **근거·경위는 규칙 본문에 쓰지 않는다.** `docs/research/` 에 두고 링크한다. (`rules.md` 는 평균 235자/줄 · 200자 초과 48%)
5. **id 는 자리가 아니라 이름이다** — 규칙을 쪼갤 때 **다음 빈 번호**를 쓰고 뒤를 밀지 않는다(R5-03 을 가르며 R5-09 신설). 번호를 밀면 바깥 인용이 조용히 다른 규칙을 가리킨다 — 실측으로 그런 인용이 3곳 있었다(`R5-03` 이 재편 뒤 전혀 다른 규칙이 됐는데 track-3prime·genBadge.mjs·research 가 옛 뜻으로 인용).
6. **볼드를 셈 단위로 쓰지 않는다** — 「규칙 63개」의 정체가 *볼드로 시작하는 최상위 불릿*이었다. 규칙에는 **id** 를 붙인다(가드 메시지·`plan.why`·research 가 같은 이름으로 가리킬 수 있다).
7. **한 불릿에 두 규칙을 넣지 않는다** — 집행 유형이 갈리면 가드를 못 붙이고, **집행 표시가 절반만 참**이 된다. 실측 정리(2026-09-02): `R5-42`(예측 라벨+안전영역) → R5-05/R5-06 · `R3-02`(강조 대상+팝) → R3-02/R3-03 · `R5-03`(에셋=씬+정지 4초) → R5-03/R5-09(`✓(B3)` 가 뒷문장에만 참이었다). **`R8-01`(external 의무 / stock 권장)은 합체가 아니다** — 한 규칙의 두 등급이고 코드도 한 줄이다(1차 목록의 오탐).

## 7. 기록

- **사용자 원문이 정본이다.** 해석이 갈리면 원문이 우선한다 — 규칙 표에 원문 열을 남긴다([stages-log.md](stages-log.md) — 3편 기준 R1~R12, 4편 U1~U8, 5편 U1~U7).
- 규칙을 고칠 때 꼬리표 **`(YYYY-MM-DD <세션> 정정)`** 로 정정 주체를 남긴다.
- 편별로 굳어진 것은 `stages.md` 에 쌓되 **편 이름 절을 새로 만들지 않는다** — 절을 편마다 더하면 구조가 F5 를 부른다. **2026-09-02 재배치 완료**: 편 이름 절 6개를 「단계별로 굳어진 것」(단계 이름 + 꼬리표 `(N편)`)과 「사용자 원문 → 규칙 (편별)」 둘로 접었다. **새 편은 절이 아니라 한 줄·한 행을 더한다.**
- 결정·조사는 `docs/research/<날짜>-<주제>/{raw,summary}.md` + `docs/INDEX.md` 한 줄.
- **집행 표시를 규칙 옆에** — `✓가드` / `△부분` / `✗사람만` / `!미구현`. 지킬 수단이 없는 규칙([rules-finish.md §12](rules-finish.md) 커버 크레딧)이 표시 없이 섞여 있으면 무엇이 자동으로 잡히는지 알 수 없다.

## 8. 추가 트랙과 후보 엔진

사용자가 기존 방식의 교체를 요청하면 해당 모듈과 호출 지시·기록 양식을 함께 교체한다. 과거 산출물·대장은 재현용으로 보존하고, 관련 없는 최신 기능을 이전 버전으로 되돌리지 않는다. (2026-09-06 사용자 지시)

단일 편의 후처리 실험은 기존 0~6을 바꾸지 않고 트랙으로 덧붙인다. 제작 단위 자체를 바꾸는 후보 엔진은 기존 엔진을 버전으로 보존한 뒤 별도 `engine` 값·스키마·가드·기준편으로 검증한다. `editorial-concept@1`은 이 절차의 첫 후보이며, 두 신규 편이 품질·시간 조건을 연속 통과하기 전까지 기본값으로 강제하지 않는다.

되돌림은 데이터에 남긴다 — `clip_option`(배경) · `inset_option`(인셋) · `gen_rejected`(기각 생성) · `graphics_disabled`(도해). 후보 엔진의 이전 입력과 컴파일된 timeline도 해시로 연결해 보존한다.
새 트랙은 **워크트리를 분리**해 시작한다(`git worktree add .claude/worktrees/<name> -b <branch> main`). 워크트리엔 `node_modules` 와 `public/pilots` 를 심링크한다 — **안 걸면 검사 결과가 통째로 흐려진다**(편마다 SKIP 수십 건).
