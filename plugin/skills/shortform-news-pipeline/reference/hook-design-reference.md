# 위성공해 후킹 — 실제 전달본의 조판 근거

도입 조판 전에 아래 **실제 영상 추출 프레임**을 열어 본다. 코드의 role 두 개나 서로 다른 색만으로 위성공해의 표현을 반영했다고 판단하지 않는다. start/resume의 `context.hook_reference`는 이 문서와 해시 확인된 프레임 경로를 제공한다. 누락·해시 불일치면 확인하지 못했다고 기록하고 복구한다. 가이드 글만 읽은 것을 화면 확인으로 간주하지 않는다.

고객 원문:
> 1차 파일럿 <위성공해>편 도입부는 초반 후킹 코멘트 ‘스타링크 아시죠? 이게 밤하늘의 별을 지우고 있다는 것 아세요?’ 여기에 말자막과 구분되는 큰 중간위치 자막과 노란 밑줄로 강조가 되었습니다. 하지만 2,3차 파일럿에는 그런 후킹 멘트의 시각적 강조가 보이지 않습니다. 1편처럼 다른 영상들도 초반 집중을 끌 수 있도록 후킹 코멘트를 시각적으로 강조할 수 있도록 부탁드립니다.

## 확인한 자료

프레임은 저장소의 기존 Git LFS 규칙으로 보관한다. 포인터만 내려받은 체크아웃은 README 설치 절차의 `git lfs pull`로 실물을 복구한 뒤 해시를 다시 확인한다.

원본 식별·SHA256·프레임별 해시는 [manifest](../../../../config/hook-reference.json)에 기록했다. 1080×1920, 약91.115초의 실제 전달본이다. 로컬 `satellite_v3` 약74초 버전을 같은 근거로 사용하지 않는다.

- [4.00초: 보조 문구만 노출](assets/hook-satellite/04-00.jpg)
- [5.50초: 핵심 문구와 밑줄 등장 중](assets/hook-satellite/05-50.jpg)
- [6.20초: 완성 조판](assets/hook-satellite/06-20.jpg)

6.20초 프레임에서 읽히는 잉크 경계(압축·안티앨리어싱에 따른 약1~2px 오차):

| 요소 | 관측 범위(1080×1920) | 해석 |
|---|---|---|
| 노란 ‘스타링크가’ | x448~633, y664~701 | 짧고 작은 보조 단서 |
| 흰 ‘별을 지운다?’ | x211~870, y737~854 | 훨씬 크고 굵은 핵심 질문 |
| 노란 밑줄 | x204~873, y880~885 | 핵심 문구 폭을 따라가는 약6px 선 |

두 문구의 중심은 약x540.5다. 눈에 보이는 글자 높이는 약38px 대118px, 보조 글자 아래에서 핵심 글자 위까지 약35px, 핵심 글자 아래에서 선 위까지 약25px다. **이것은 CSS font-size·line-height 실측이 아니다.** 문구가 짧고 두 글자 덩어리의 크기 차가 크며, 주변 빈 공간과 배경이 핵심 질문을 받쳐 준다. 말자막은 아래 별도 트랙에 유지된다.

원본 서체명·굵기 값은 확인되지 않았다. 등록된 Pretendard 700/800은 재현 검토에 사용할 대체 후보이며 원본 서체라고 단정하지 않는다. GmarketSans도 등록되어 있지만 프로젝트 기본 글꼴이라는 이유만으로 자동 선택하지 않는다. CSS 크기·자간을 선택한 뒤 원해상도와 모바일 축소 화면에서 실제 획·폭·위계를 비교한다.

노란색은 압축 프레임에서 대략 RGB(255,209,105) 부근이다. 현재 공통 `#FFD16A`는 이 관측을 바탕으로 선택한 근사값이며 원본 소스의 정확한 색 코드가 아니다.

기존 0.1초 간격 관측: 보조 등장3.2~3.4초 → 보조 유지 → 핵심 등장5.0~5.2초 → 밑줄 성장5.2~5.8초 → 완성 유지5.8~6.8초 → 퇴장6.8~6.9초. **다른 영상에 복사할 타이밍 규격이 아니다.** 이 저장소의 세 정지 표본만으로 전체 모션을 검증했다고 주장하지 않는다.

## 제작에 옮길 원칙

1. 첫 발화의 핵심을 짧은 화면용 구절로 편집한다. 나레이션 전체를 큰 문단으로 쌓지 않는다. 사실·조건·불확실성은 보존한다.
2. 먼저 핵심이 어디인지 정하고 서체·굵기·크기 비율·줄 간격·정렬·주변 여백을 함께 설계한다. 보조 문구는 도움이 될 때 사용한다. 두 줄·두 역할·노란 보조+흰 핵심을 매번 강제하지 않는다.
3. 위 사례를 재현 검토할 때에는 작은 보조와 큰 핵심의 뚜렷한 차이, 압축된 문구 묶음, x540 중심과 중앙 부근의 여백을 출발점으로 삼는다. 관측 잉크 높이를 그대로 폰트 크기에 넣거나 64/104 고정 프리셋으로 대체하지 않는다.
4. `rows`에 각 줄의 서체·굵기·크기·자간·색·행 높이·간격·정렬을 명시한다. 줄별 등장 사건이 달라도 전체 묶음의 위치가 튀지 않게 공간을 예약한다. 필요 없는 보조 줄은 만들지 않는다.
5. 밑줄은 선택한 강조 구절의 실제 조판 폭에 붙인다. 배경 핵심 피사체와의 관계, 말자막·로고·출처·실제 모바일 UI 충돌을 함께 확인한다. 중앙선을 좌측으로 밀거나 모든 정보를 작은 safe rectangle에 몰지 않는다.
6. 해당 영상의 발화 앵커로 등장·밑줄·유지·퇴장을 정한다. 정지 화면으로 조판을 먼저 확인하고, 이후 승인된 짧은 샘플에서 읽기 시간과 리듬을 확인한다.

구조·폰트·폭 검사 통과는 디자인 승인과 다르다. [후킹 계약](hook-overlay.md)의 공용 경로를 사용하고, 실제 비교에서 서체·위계·구도가 맞지 않으면 코드 통과 상태여도 조판을 수정한다.
