# 실물 검수·수정·완료

기사 위임 제작의 내부 완료 계약이다. 제작자는 설명·자료·새 도해·레이아웃·모션·음향의 해결 표현을 선택한다. 특정 부품·장면 수·고정 레이아웃 사용을 통과 조건으로 만들지 않는다. 사용자는 완성 시안과 중요한 방향 선택을 본다.

[설명·정보 디자인 검수 보완](quality-review.md)을 함께 적용한다.

## 검수 역할

- TTS 전 `editorial-judge`: 원고·자료 후보에서 읽힌 이야기와 story/concepts·facts를 대조한다. 전체 이야기와 선행 개념·결론·정보량을 확인하며, 아직 없는 영상의 몰입도를 통과시키지 않는다.
- 렌더 전 `shot-judge`: 원해상·모바일 프루프와 가능한 연속 구간을 확인한다. 이 검수는 제작 개선에 쓰며 완성 MP4 검수로 자동 수입하지 않는다.
- 최종 `shot-judge`: **검수 대상 MP4에서 추출한** 원해상·1/3 모바일 표본과 실제 연속 재생으로 자료 적합성·설명·위계·발화와 등장/퇴장·속도·easing을 확인한다.
- 최종 `fact-check`: MP4의 내레이션·자막·도해·영상이 주장하는 수치·조건·출처·불확실성을 전체 시간축에서 facts와 대조한다. 원문에 필요한 근거가 없으면 미검수/결함으로 남긴다.
- 최종 음향: 실제 오디오를 들을 수 있는 독립 검수자와 도구를 지정한다. `audio-reviewer`는 보고서의 역할명이며 새 자동 호출 에이전트 이름이 아니다. 지정된 shot-judge가 청취 도구를 사용할 수 있으면 별도 음향 보고서를 반환할 수 있다. 청취 기능이 없으면 `incomplete`로 남긴다. 발음·호흡·BGM·SFX를 실제로 듣고 최종 MP4의 음량·문제 구간 측정도 대조한다.

호출 권한과 시점은 [agents.md](agents.md) 및 저장소 지침을 따른다. 새로운 에이전트 호출 권한을 이 문서가 추가하지 않는다. 기존 리뷰 원문은 보존한다. 보거나 듣지 않은 범위를 선언만으로 채우지 않는다.

## 실물에서 읽힌 흐름을 먼저 확인

제작자는 장면별 프루프 외에 현재 원고·자료·모션·음향이 실제 길이로 이어지는 시안을 검수 입력으로 제공한다. 현재 재생 가능한 프리뷰나 요청된 완성 렌더를 재사용한다. 별도 러프컷 렌더·고정 횟수의 중간 렌더를 의무화하지 않는다. 프레임 시트만 있다면 연속 경험 검토는 아직 없는 것이다.

`shot-judge`에게는 먼저 시안 경로·버전·분량·확인 도구를 전달한다. 첫 응답에서 **무엇을 이해했고, 어떤 궁금증이 이어졌으며, 어디서 정보나 관심의 진전이 멈췄는지**를 시점과 함께 받는다. 그 뒤 같은 검수자에게 story/concepts·facts·선택 이유·기존 이슈를 전달해 의도 및 사실 대조와 재검수를 이어간다. 이미 의도를 본 검수라면 그 사실을 기록한다. 이를 이유로 새 검수자를 계속 추가하지 않는다.

## 현재 시안의 입력 명령

`resume`의 `context.work.review_inputs`에서 현재 입력을 선택한다. `preview`는 `proof`에 기록된 중간 시안이고 `render`는 기술 검증된 최종 MP4다.

```bash
node scripts/produce.mjs review-input <id> --source preview --phase experience
# 현재 렌더의 검수라면 --source render 사용
# 위 입력과 실제 확인 가능한 도구를 지정 검수자에게 전달하고 첫 관찰을 받는다.
node scripts/produce.mjs review-input <id> --source preview --phase intent
```

`experience`는 실물·시간·버전만 반환한다. 검수자에게 현재 호스트에서 실제 사용할 수 있는 확인 수단을 함께 전달한다. `intent`는 이번 편의 사실·원고·개념·자료·이전 관찰 경로를 더한다. 두 입력의 receipt와 실물 해시가 같은지 확인하고 대조를 이어간다. 입력이 바뀌었다면 새 시안을 먼저 본다. experience에는 과거 사례를 추가하지 않는다. intent에는 `context.reference_library`의 지정 공통 세트를 함께 제공하여 설명·미술·모션 기준을 대조한다. 임의의 과거 평가 결과를 이번 편의 판정으로 가져오지 않는다.

명령은 읽기 전용이다. 파일을 렌더하거나 에이전트를 호출하지 않고 관찰·확인 범위도 채우지 않는다. 이미지 표본에는 연속 시청 범위가 없으며, 중간 영상이나 음향 파일도 최종 MP4 검수로 수입하지 않는다. 없는 파일·낡은 입력은 새로 만들어진 것으로 처리하지 않는다. P5 관찰은 기존 제작 노트나 `reviews/`의 원문에 보존하고, P7은 아래 최종 보고서 계약에 연결한다.

전체 이야기·자료 구성·도해 표현·모바일 위계·타이밍·음향의 관찰을 구별하되 한 점수로 평균 내지 않는다. 오래 유지한 화면도 이해를 진전시킬 수 있고 빠른 전환도 혼란을 줄 수 있다. 시청자의 이해와 관심에 실제 어떤 일이 생기는지 근거로 남긴다. 검사표의 항목 수나 실사 비율은 목적이 아니다.

## 시청·청취 수단 확인

착수 때 현재 호스트와 검수 에이전트가 실제로 쓸 수 있는 도구를 확인한다. 로컬 MP4 또는 허용된 입력을 받을 수 있는지, 영상의 시간 흐름과 음향 중 무엇을 인식하는지 구별한다. 미검증 도구는 첫 실제 사용 결과에서 입력 버전·확인 구간·내용 관찰이 나오는지 확인하고 그 응답을 증거로 보존한다. 알려진 짧은 자료로 기능을 확인할 수 있지만 그것을 해당 편의 검수로 계산하지 않는다.

도구 이름이나 설명만 있으면 후보이며 시청·청취 가능으로 확정하지 않는다. 브라우저 재생 종료, FFmpeg 디코드, 프레임 표본, 전사·LUFS 측정으로 `playback_ranges`나 `listened_ranges`를 채우지 않는다. 장면 분석 도구도 실제 확인 방식과 범위를 밝히며 자동으로 연속 시청과 동등하게 취급하지 않는다.

수단이 없으면 가능한 표본·원고·측정 검토를 수행하고 연속 시청·청취는 미검수로 남긴다. 제작과 수정은 계속할 수 있으나 완성 검수 완료를 주장하지 않는다. 도구 연결의 미해결 사항을 사용자에게 중요한 한계로 알린다. 외부 업로드나 유료 실행은 기존 사용자 권한과 도구의 입력 조건을 따른다.

## 실제 명령

먼저 [제작 상태](production-state.md)의 render를 기록한다. `finish render`는 MP4의 해상도·FPS·전체 프레임 수·영상/음향 길이·전체 디코드를 검사한다. 내용이 좋은지는 이 검사로 판단하지 않는다.

```bash
# JSON만 출력할 때는 npm 로그가 섞이지 않는 직접 명령 사용
node scripts/produce.mjs review-template <id> review_visual
npm run produce -- begin <id> review_visual --output news/<id>/02_production/reviews/visual-r1.json
# 시각 검수는 먼저 실물 관찰을 받고, 이어 facts·의도·수정 이슈와 대조한다.
# 실제 도구 결과를 raw_report와 evidence로 보존하고 응답을 JSON에 기록한다.
npm run produce -- finish <id> <token>
```

`review_audio`, `review_facts`도 같은 방식이다. 템플릿은 현재 MP4 경로·SHA256·렌더 receipt·시작 HEAD만 채운다. 관찰·독립 여부·확인 범위는 비어 있고 판정은 `incomplete`다. 보고서 파일 하나를 begin의 출력으로 지정하고 원문·표본·측정 로그·facts는 증거로 연결한다. 기존 파일을 덮어쓰지 않는다.

## 보고서 계약

| 필드 | 기록할 내용 |
|---|---|
| `artifact` | 현재 MP4의 `path`, `sha256`, `render_receipt`. 템플릿 값을 유지한다. |
| `source_commit` | 렌더 시작 HEAD. 정확한 제작 입력은 run.json의 파일 해시를 함께 읽는다. |
| `reviewer` | 실제 검수자 `id`, 분야별 `role`, 제작과 분리된 검수인지 `independent`, 실제 사용한 `tool` |
| `raw_report` | 검수 응답 원문 파일의 `path`, `sha256`. 원래 이슈 문구를 수정하거나 요약해 대체하지 않는다. |
| `evidence` | 원해상·모바일 표본, 실제 재생/청취 도구 기록, 측정 로그, facts 등 `{path, sha256}` 배열 |
| `coverage` | 아래의 실제 확인 범위. 모든 구간은 프레임 기준 `[from,end)`이며 end는 포함하지 않는다. |
| `verdict` | `pass`, `changes_requested`, `incomplete`. 차단 결함이 있으면 pass를 쓸 수 없다. |
| `findings` | `{id, severity, range, observation}` 배열. id는 보고서 안에서 유일하고 `:`를 쓰지 않는다. observation은 관찰 원문. |
| `rechecks` | 기존 이슈의 수정 결과를 실제 다시 확인한 기록. 아래 참조. |

`coverage.original_frames`와 `mobile_frames`는 `{frame, evidence: "파일 경로"}` 배열이다. 원해상과 프로필 크기의 1/3 해상도를 실제 파일에서 확인한다. 각 개념의 대표 상태를 최소 한 번씩 보고, 긴 개념이나 변화가 많으면 필요한 표본을 더 선택한다. 표본 수는 표현의 장면 수를 제한하지 않는다.

`playback_ranges`는 실제 연속 시청, `listened_ranges`는 실제 최종 음향 청취, `fact_ranges`는 최종 영상의 주장·사실 대조 범위다. 각각 빈 배열로 시작한다. 완성 판단에는 분야별로 전체 영상 범위가 확인돼야 한다. 여러 번 나누어 볼 수 있고 **같은 MP4·같은 입력**의 독립 검수 범위는 합쳐 쓴다. 입력이나 실물이 바뀌면 과거 범위를 자동 재사용하지 않는다.

`audio_measurement`는 evidence에 연결된 최종 MP4 측정 로그 경로다. 측정 전이면 null. 기존 `npm run audio:measure -- <mp4> --win <이름:시작초:길이초>` 등 실제 도구 출력을 보존한다. LUFS·peak 수치나 파형만 보고 청취했다고 쓰지 않는다. 사실 보고서는 현재 `facts.md`를 evidence에 포함한다.

`blocking`은 사실 오류, 설명을 오해하게 하는 표현, 모바일에서 읽지 못하는 정보, 깨진 미디어·타이밍·음향처럼 완성본 제출 전 수정해야 할 결함이다. 중심 질문과 설명·결말이 연결되지 않아 한 편의 목적을 달성하지 못하는 문제도 전체 범위의 결함으로 남긴다. `minor`는 제출을 막지 않는 작은 관찰이며 완료 기록과 사용자 설명에 남긴다. 통과시키기 위해 심각도를 낮추지 않는다.

## 수정과 재검수

제작자는 관찰된 문제를 읽고 원고·자료·개념 순서·화면·모션·음향 중 어디를 바꿔야 해결되는지 선택한다. 전체 이야기의 문제를 부품이나 라벨 수정으로 해결할 수도 있지만, 실제 흐름이 좋아졌는지 다시 확인해야 한다. 원래 계획대로 구현됐거나 `minor`라는 이유만으로 유지하지 않는다. 중요한 관찰에는 기존 제작 노트에서 **수정 범위와 이유, 또는 유지 이유와 한계**를 응답한다. 모든 관찰마다 새로운 문서를 만들거나 매번 원고를 다시 쓰지는 않는다.

`context.work.observations`의 원문과 이슈를 읽고 필요한 변경을 실행한다. 파일 변경으로 낡아진 결과는 `context.work.refresh`에서 확인하며, 파일 관계 밖의 의미 영향은 `invalidate`로 표시한다. 새 입력으로 시안을 갱신한 뒤 검수자에게 원래 관찰과 변경된 실물을 연결한다. 다음 수정 범위는 제작자가 정하고, 검수자의 구체적 처방이나 사용자 추가 지시를 기다리는 단계로 바꾸지 않는다.

```bash
npm run produce -- resume <id>
# 편별 코드·자료·원고·음향에서 적절한 해결을 수행하고 영향받은 결과를 갱신한다.
npm run produce -- resolve <id> <검수receipt:이슈id> --reason '실제 변경과 이유' --from 300 --end 360
# 새 검수 JSON을 begin/finish로 기록
npm run produce -- complete <id>
```

resolve는 **현재 렌더에 대한 제작자의 수정 설명**이다. 해결 통과를 뜻하지 않는다. 편집으로 시간이 이동하면 현재 MP4의 수정 범위를 지정하고 이동 이유를 적는다. 표현 변경이 불필요한 오판이면 이유를 적고 같은 실물을 독립 재확인한다.

새 검수자의 `rechecks` 항목:

```json
{
  "issue": "검수receipt:이슈id",
  "resolution_id": "resolve가 반환한 id",
  "range": [300, 360],
  "verdict": "fixed",
  "observation": "실제로 다시 확인한 결과 원문"
}
```

`fixed` 또는 `open`을 쓴다. 최신 수정 기록과 같은 실물, 수정 범위 전체의 실제 재생/청취/사실 대조가 필요하다. 부분 재검수는 그 구간만 기록한다. 같은 실물·입력의 이전 전체 검수와 합칠 수 있다. 새 보고서에 이슈를 생략해도 원래 이슈는 사라지지 않는다. 새 렌더에서는 기존 차단 이슈도 현재 실물의 수정·재검수에 연결한다.

## 완료를 읽는 법

- `incomplete`: 렌더·검수가 미기록/낡음, 범위 누락, 미해결 차단 이슈 또는 증거 변경이 남아 있다.
- `ready`: 현재 실물과 독립 검수·수정 근거가 갖춰졌다.
- `complete`: 제작자가 `produce complete`로 그 근거를 기록했다. 추가 사용자 승인 단계가 아니다.

완료 뒤 소스·MP4·검수 증거가 바뀌면 현재 판정은 다시 incomplete가 된다. 과거 완료 기록과 원래 이슈는 보존한다. 원해상 표본·연속 재생·청취·사실 확인 범위, 남은 minor 관찰은 `status/resume --json`의 completion에서 읽는다.

이 코드는 파일·범위·보고서 연결을 확인한다. 실제로 사람이/에이전트가 보거나 들었는지, 독립적으로 판단했는지, 표본이 해당 MP4에서 추출됐는지와 표현 품질 자체는 도구 기록과 검수자의 정직한 관찰을 필요로 한다. 수동 JSON 변조를 막는 보안 감사 시스템은 아니다. 합성 fixture를 실제 뉴스 검수로 제출하지 않는다.

`out:deliver`는 납품본의 보관·복사 도구다. 그 대장 상태나 파일 존재가 자동 검수 완료 판정을 대신하지 않는다.

## 사용자 확인 후 마감과 보관

사용자가 영상 시청 확인과 마무리를 지시한 경우 그 원문을 `00_brief/closeout-request.txt`에 보존하고 `02_production/closeout.json`에 해당 편·완성 파일·썸네일의 해시와 마감 근거를 기록한다. 사용자의 확인 범위를 확대 해석하거나 과거 자동 검수 보고서를 pass로 덮어쓰지 않는다. 사용자 확인을 모든 편의 추가 승인 단계로 요구하지 않는다.

마감 기록은 `schema_version: "1.0"`, `pilot`, `status: "closed"`, `basis: "user-confirmed"`, `recorded_at`, `raw_request: {path, sha256}`, `artifacts: [{path, sha256}]`를 사용한다. 경로는 저장소 상대 경로다. `status/resume`의 `delivery`가 기록과 파일 해시를 대조한다. `closed`는 사용자 마감, `changed`는 확정 원문·파일의 유실/변경, `invalid`는 기록 오류다. `completion`은 기존 자동 검수 계약이며 사용자 마감과 별개다. 자동 검수 미완료만 보고 사용자 마감 자체를 취소하거나 재시청·재제작을 요구하지 않는다.

마감 때 `pilots/<id>/pilot.json`에 완성본 `versions[]`·해시·제작 완료일·사용자 확인 근거를 등록하고 상태를 `delivered`로 맞춘다. 이 저장소의 `delivered`는 파일럿 완성본 확정이며 외부 게시·고객 승인으로 확대하지 않는다. `out:deliver`로 정해진 이름의 파일·부속물·MANIFEST·LATEST와 주 작업트리 보관본을 만들고 `pilots`로 대장을 갱신한다. 기존 `deliver/v<N>`에 변경할 기록이 있으면 새 판에 동일한 영상·썸네일을 복사해 묶고 원래 판은 보존한다.

수집 원본은 `01_input/`, 선택·가공·검수 자료는 `02_production/`에 둔다. 이미 검수 근거로 해시가 고정된 문서·실행 이력은 변경하지 않고, 정리할 때의 경로 대응과 보존 사유를 남긴다. 공통 지침 수정은 버전 갱신·검증 후 저장소와 설치본 반영 여부를 기록한다.
